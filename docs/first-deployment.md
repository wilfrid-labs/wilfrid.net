# First deployment and initial GitHub setup

One-time setup record: mark steps complete after verification. Use [maintenance](maintenance.md) for ongoing operations and [CONTRIBUTING.md](../CONTRIBUTING.md) for routine PRs.

Use the configured website domain for the deployment smoke test. Cloudflare’s optional `workers.dev` address is explained under [deployment addresses](architecture.md#deployment-addresses); enabling it is not a prerequisite for serving a configured custom domain.

Repository settings, secret contents, token permissions, environment protections, CI execution, and deployment have **not** been verified remotely. Complete these steps in order; no settings were changed by this implementation.

1. **Before merging, inspect the existing Cloudflare token and destination.** Preserve the existing secrets. Verify the token is valid, limited to the intended account, and has the required account-level **Workers Scripts: Edit** permission for this assets deployment. Do not add DNS, zone, D1, or Workers Routes write access for a `workers.dev` deployment. Verify any additional permission only if the API actually requires it; do not broaden scope speculatively. Check that the `wilfrid-net` Worker name and configured website domain target the intended deployment. If using the optional `workers.dev` address, also check its account subdomain. An existing Worker with conflicting configuration may require separate owner action. See [Cloudflare's external CI guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/). See [security notes](../SECURITY.md#credentials-and-incidents) for rotation.
2. **Settings → Actions → General.** Verify Actions are allowed and policy permits the SHA-pinned official checkout/setup-node Actions. Set default workflow token permissions to read-only repository contents and packages. Disable Actions creating and approving PRs unless needed. Avoid sending write tokens or secrets to untrusted fork PRs. Fork policies can require a maintainer to approve the first CI run.
3. **Settings → Environments → production.** Preserve the existing environment, all three secrets, and protection rules. Restrict deployment branches/tags to the branch `main`, where the plan supports it. Retain existing approvals; no new approval requirement is needed for this solo site.
4. **Settings → Security → Advanced Security / Code security** (label varies by plan). Enable or verify the dependency graph, Dependabot alerts, and Dependabot security updates. The monthly Actions schedule is version maintenance, not a replacement for security updates.
5. **After reviewing the local changes, commit them on a feature branch, push, and open a PR targeting `main`.** Wait for the `CI` workflow's `validate` job to pass. GitHub must have seen the check run before it can reliably be selected in a ruleset; do not guess its displayed check name.
6. **Settings → Rules → Rulesets.** Create or update an active branch ruleset targeting `main`. Require PRs and the exact check displayed for `CI` / `validate` after that run; select GitHub Actions as the expected source where available. Use zero required approving reviews where supported for a sole developer. Block force pushes, restrict deletions, and avoid unnecessary bypass permissions. Verify enforcement and plan support rather than assuming the ruleset is active.
7. **Settings → General → Pull Requests.** Prefer squash merging and automatically delete merged feature branches. Merge the passing PR only when ready: that push to `main` immediately triggers the first production deployment, subject to existing environment protections.
8. **Inspect Actions → Deploy.** Verify install/check/build/deploy success, the checked-out commit, and its website URL (`workers.dev` if enabled, and the configured custom domain where applicable). Smoke-test the page and email reveal/open/copy behavior. Local validation cannot prove these remote checks. See [maintenance](maintenance.md#github-actions-deployment) for retries.
